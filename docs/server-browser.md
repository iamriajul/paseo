# Server browser

The server browser is a browser the daemon drives on its own host. Agents drive it through the usual MCP browser tools, and every client (desktop, web, phone) watches the same tab live and can take it over. It keeps working with every app closed, and `localhost` in it is the daemon host's localhost, so workspace dev servers open without a tunnel.

It is experimental and off by default.

## Turn it on

Settings → the host → Agents → Browser tools card → **Server-side browser (experimental)**, then pick an engine. Any engine also turns on Browser tools: the server browser only serves agents through them. The choice is a host setting (`serverBrowser.enabled` and `serverBrowser.engine` in that host's `config.json`), because the daemon decides where tabs open. A host turned on before engines existed keeps Headless (light).

| Engine           | `engine`         | What runs                                                                              | Workspaces                             | Logins persist                                                                    |
| ---------------- | ---------------- | -------------------------------------------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------- |
| Headless (light) | `headless`       | Playwright's headless shell, started by the daemon                                     | a browser context each, nothing shared | cookies and localStorage, saved by the daemon                                     |
| Managed Chrome   | `managed-chrome` | real Google Chrome, started by the daemon, in a window (Window) or headless (Headless) | share one profile and cookie jar       | everything, in Chrome's own profile                                               |
| Existing browser | `existing`       | a Chrome already running on the host (`serverBrowser.cdpUrl`, default port 9222)       | share that browser's cookie jar        | whatever that browser keeps; the daemon never closes it or touches its other tabs |

Pick Managed Chrome when a site has to treat the browser as a person's (Google sign-in, captchas), Existing browser to reuse a Chrome you already signed into, and Headless (light) for the least memory and workspaces kept apart. Engines live in `packages/server/src/server/server-browser/engines.ts`; adding one is a kind, its traits and a start function there.

Headless (light) needs a Chromium. The daemon looks, in order, at:

1. `serverBrowser.executablePath` in `config.json`, or `PASEO_SERVER_BROWSER_EXECUTABLE`;
2. Playwright's browser cache (`~/.cache/ms-playwright`, or `PLAYWRIGHT_BROWSERS_PATH`): the newest `chromium_headless_shell-*`, then the newest `chromium-*`;
3. `chromium`, `chromium-browser`, `google-chrome` or `google-chrome-stable` on `PATH`.

If none is found, the tool call and the Settings row say so. Install one as the user the daemon runs as:

```bash
npx playwright install chromium-headless-shell
```

Managed Chrome needs Google Chrome: `PASEO_SERVER_BROWSER_CHROME`, else `google-chrome`, `google-chrome-stable`, `chromium` or `chromium-browser` on `PATH`. Existing browser needs a Chrome started with `--remote-debugging-port`.

Headless (light) and Managed Chrome always start their own process with their own profile under `$PASEO_HOME/server-browser`, so a Chrome you run yourself (for example one on port 9222) is never touched unless you pick Existing browser.

## What it does

- **Routing.** `browser_new_tab` takes an optional `target`: `desktop` opens the tab in a connected desktop app's Browser (the user is at the laptop and wants to see the tab, or it needs the laptop's logins or localhost), `server` in the server browser (works with every app closed and the laptop asleep, watchable from the phone). Without `target` the host's **Default browser for agents' new tabs** decides (`serverBrowser.newTabTarget`, its own row in the Browser tools card): Automatic (the default) picks the desktop app while one with a Browser is connected and the server browser otherwise; Server and Desktop always pick that one. The setting is independent of the engine and of the server browser switch, and every combination works: with the server browser off, Automatic means the desktop app and Server is unavailable, which the row says. An unavailable target fails and names what is available; nothing falls back. A tab stays on the browser it opened in: commands on a server tab go to the server browser, any other tab to the app that owns it. `browser_new_tab` and `browser_list_tabs` say where each tab runs (`location=server` or `location=desktop`). An app that reconnects registers its new connection while the old one lingers unanswered for the reconnect grace (90 s). `browser_list_tabs` asks every connection, so the broker takes each app's tabs from the first of its connections that answers (`appId`, the session's client id). Before this, the silent connection failed the whole list after its timeout, and the router showed the server tabs alone, while `browser_new_tab` still opened tabs on the newest connection. When a connected desktop app answers nothing, the list has the server tabs and an `incomplete` note saying the desktop's are missing. An engine that is not there (an Existing browser at an address nobody answers, a browser that closed under a command) fails with `browser_no_host` and `retryable: true`, the code the broker gives an app that disconnected; the next tab starts or reattaches it. With the server browser off, `target: "server"` fails and no browser starts. See `packages/server/src/server/server-browser/router.ts`. Through v0.15.908, every new tab opened in the server browser while it was on, even with a desktop app connected; that kept tabs alive with the laptop closed, but sent tabs the user wanted to see on the laptop to a browser they were not looking at.
- **Commands.** The server browser runs the same automation engine as the desktop app's Browser, vendored from `packages/desktop/src/features/browser-automation` (the server cannot import desktop). Snapshots, `@eN` refs, actionability waits and errors are identical on both hosts. After an upstream change to the desktop engine, run `node scripts/sync-server-browser-engine.mjs`; `engine-sync.test.ts` fails until you do.
- **Viewing.** An agent's tab opens in its workspace in the background on every client, as a tab with a server icon. A tab the daemon closes leaves the workspace, and closing its workspace tab (its X, Close tab, close others/left/right) closes it on the daemon for every client, as the menu's Close tab does, so its page stops and it leaves `browser_list_tabs` and the tab limit. A tab opens on its page with no blank entry behind it, so Back is off until the page navigates. A load that fails shows the other Browsers' card with Chromium's error and Retry, and the URL bar keeps the URL it tried: the tab reports `loadError` when its main frame commits Chromium's error page (`frame.unreachableUrl`). The error comes from `Page.navigate`'s answer, or, for a load the page started, from Chrome's error page; the headless shell's error page is empty, so there that card names only the URL. The toolbar has back, forward, reload (Stop while the page loads), the URL, the other Browsers' device sizes, and a menu with **Clear browser data** and **Close tab**. The sizes are the agents' default (1280×800, every new tab's), Responsive, and the desktop pane's phone, tablet and desktop presets (`desktop/browser/device-presets.ts`); phones and tablets emulate a mobile device (touch, the page's meta viewport, 2× pixels). A size is the tab's, so every viewer and the agent see it. Responsive belongs to the viewer that picks it: it sizes the page to that viewer's pane and follows its resizes, and another viewer's choice ends it.
- **Idle tabs suspend.** A tab no agent command or viewer touched for 10 minutes is suspended: the daemon reads its scroll position and takes a JPEG of the page, then closes its target, which frees its renderer. The tab stays in the workspace (with a moon icon) and in `browser_list_tabs` (marked `suspended`), with its title and URL. A viewer that opens it gets that frame at once, while the tab reopens in the same workspace context (cookies and storage as before), loads the same URL and scrolls back; the live page replaces the frame when it paints. An agent's command on a suspended tab reloads it first, and the tool's answer starts with a note that the page is new: what the site did not save (form input, in-page state) is gone, and earlier `@eN` refs are stale. The back/forward history is not kept: CDP can only rebuild it by loading every entry again, so Back is off after a reload. A watched tab never suspends; a tab watches only while it is on screen in some client, and one kept mounted behind another tab streams nothing (`use-screencast.ts`). Through v0.15.912 a hidden tab kept a 100×100 stream open, so every tab a client had shown stayed watched. A workspace with no live tab closes its context, and then the browser exits, by the rules in Limits, so a host whose tabs are all suspended runs no browser; headed Managed Chrome closes at once, because it quits by itself a moment after its last window closes and a viewer arriving in that moment would find it dying. On an Existing browser, suspending closes only the window Paseo opened for that tab, as closing it did. Through v0.15.912 an idle tab closed after 30 minutes and left the workspace; the 10 minutes is justified by the measurement in Cost.
- **Suspended tabs survive a restart.** Each one is written to `$PASEO_HOME/server-browser/suspended-tabs/<browserId>.json`, frame included, in a directory only the daemon's user can read (the frame shows signed-in pages). A graceful shutdown suspends the open tabs too, within 3 s, so they all come back suspended under the same ids; a killed daemon brings back only the tabs already suspended. Turning the server browser off, or changing the engine, closes them and deletes the files.
- **Taking over.** On desktop and web, mouse, wheel, keyboard and paste go to the page. App shortcuts with a modifier (the command center, closing and switching tabs) still work while the viewer has focus, and the page never gets their key; shortcuts a text field leaves alone (`?`, plain keys) go to the page, because the viewer counts as a text field for shortcuts (`keyboard/focus-scope.ts`): the remote page may have one focused. On a phone, a tap clicks, a drag scrolls, a long press right-clicks, and the keyboard button opens a "Type into the page" bar.
- **Popups.** A page a tab opens (`window.open`, a `target=_blank` link, noopener or not) becomes a server tab of the same workspace at its opener's size, with `openerBrowserId` naming the opener: `Target.targetCreated` reports it with an `openerId`, and the browser adopts every page whose opener is one of its own. It opens next to its opener, in front on the client whose focused tab is the opener (the one that clicked) and in the background on the others. Past the tab limit the popup is closed and the opener's console says so. On an Existing browser a page the owner's tabs open stays the owner's.
- **Uploads.** While a viewer watches, a page's `<input type=file>` asks that viewer instead of opening Chromium's chooser, which nobody sees (`Page.setInterceptFileChooserDialog`, a per-page setting, so an Existing browser's own windows keep Chrome's chooser while no viewer watches). The viewer picks files on its own device with the composer's picker, and sends their bytes (`browser.server.tab.file_chooser.answer`, up to 50 MB per answer); the daemon writes them to `$PASEO_HOME/server-browser/uploads/<browserId>/` on its host and sets them on the input (`DOM.setFileInputFiles`). That folder goes with its tab. An Existing browser therefore has to run on the daemon's host to read them. `showOpenFilePicker` has no input to set and is not offered. Agents keep `browser_upload` with host paths.
- **Console.** The actions menu's Show console opens the tab's console under the page: the lines agents read with `browser_logs` (the tab keeps its last 200), errors and warnings coloured. The panel polls `browser.server.tab.logs` every second while it is open, asking only for lines after the last one it has (`seq`); Clear empties this viewer's panel. A tab reads at most 1,000 console messages (or 1 MB of text) a second, which keeps a page's start-up bursts, exceptions included (`console-budget.ts`). Past that it turns the CDP Runtime domain off, so the page stops sending them, and turns it back on once the pause is over and the events already in flight have stopped arriving: 2 s at first, doubling up to 5 minutes while the page keeps it up. A warning line then says how many messages were dropped; messages logged during the pause are not counted. A page logging in a tight loop sends Chrome's browser process events faster than it can forward them, however fast the client reads, and Chrome holds the rest in memory. On the dev box a tab on a 50 MB/s console page held Chrome at 0.4–1.0 GB after 45 s without the budget; with it, Chrome peaked at 90–200 MB in three of four runs (940 MB in one) and was back at its 60 MB baseline by then in three. Chrome still takes one burst before the off reaches the page, and a new tab can still wait for Chrome to drain it: a second tab did not open within 10 s during any of those runs, with or without the budget. A React-style error loop (500 errors a second) stays under the budget and never slowed Chrome.
- **Screenshot element.** The toolbar's camera button picks an element the same way and copies its crop to the clipboard, as the other Browsers do: through Electron's main process on desktop, as a PNG clipboard item in a browser, with `expo-clipboard` on a phone. Without a crop it copies the element's text.
- **Annotating.** The toolbar's Annotate element button (the other Browsers' pointer icon and copy) arms a picker in the page. Pointing highlights the element under the pointer on the real page, with the same outline and label as the web Browser; on a phone a touch points, a drag moves the highlight instead of scrolling, and lifting the finger picks. A click or tap picks the element without pressing it, then the usual note card opens and Attach adds a `browser_element` attachment identical to the other Browsers' (selector, text, HTML, styles, parents, React source when a dev build exposes `_debugSource`) plus a crop of the element's visible part, which the Electron pane also sends and the web pane cannot. Escape, the button, a navigation or the client disconnecting cancels; keys and paste stay out of the page meanwhile, and the wheel still scrolls.
- **Opening a service.** While the server browser is on, every URL the workspace would open in its Browser (the scripts menu's Open, the ports panel, localhost links in chat) opens in a server tab instead. The toolbar has the other Browsers' services menu (Open preview first, then each `paseo.json` service, a stopped one started first) and the URL bar shows the service's name, as in [Browser workspace services](fork-decisions.md#browser-workspace-services). A service opens in the same tab at `http://localhost:<port>/`: the server browser runs on the host, so that is the service itself, with no tunnel or service proxy between.
- **Open on this computer.** On the desktop app, a server tab on a localhost URL has the desktop Browser's Open on this computer menu, on Android the same menu as Open on this phone ([On a phone](browser-localhost-routing.md#on-a-phone)), and on iOS and the web build Open in browser, which opens the host's public URL for the page ([Public URLs](browser-localhost-routing.md#public-urls)): it forwards the page's port, every loopback port the page used on the host, and ports added by hand to the laptop at the same numbers, then opens the page in the system browser. See [Open on this computer](browser-localhost-routing.md#open-on-this-computer). Through v0.15.912 server tabs had none, because the host's ports are not on the viewer's machine; the forwards now ride the TCP tunnel desktop Browser tabs already use, which needed only the port set from the host.

## How it works

```
agent ──MCP──> daemon ──ServerBrowserRoutingBroker──> ServerBrowserHost
                                                        │ one browser per host, from the engine
                                                        │ CDP over --remote-debugging-pipe, or a WebSocket (Existing browser)
client <──WebSocket: browser.server.* RPCs, binary 0x40 JPEG / 0x42 video, 0x41 acks──┘
```

- **One browser per host.** Every engine yields the same CDP browser (`shared-chromium.ts`), so tabs, the viewer and the MCP tools never see which one runs. The host's first tab starts it or connects to it.
- **Headless (light): one browser context per workspace.** each workspace's first tab opens a CDP browser context in it (`Target.createBrowserContext`). Contexts never share cookies, storage or renderer processes; they share the browser, GPU, network and zygote processes, so a second workspace costs only its pages. v0.15.904 ran one Chromium per workspace with a persistent profile, which kept IndexedDB with no code of ours but paid a whole browser process tree per workspace; that tree is the cost this design removes. See `shared-chromium.ts`.
- **Headless (light) storage is saved by the daemon.** Contexts live in memory, so the daemon writes each workspace's cookies (session cookies included) and localStorage to `$PASEO_HOME/server-browser/storage/<workspaceId>.json`, in a directory only its user can read, and loads them into the workspace's next context. It saves 2 s after a tab navigates, every 30 s while the workspace has tabs (a login by `fetch` sets a cookie without navigating), when the context closes, and on shutdown; an unchanged state is not rewritten. localStorage of an origin no tab has open is read and restored from a hidden page whose every request is answered with an empty document, so the origin's server need not run and its scripts never execute (Playwright's storageState does the same). IndexedDB, sessionStorage, Cache Storage and service workers are not saved: a login kept only in IndexedDB (Firebase Auth's default) does not survive the context closing. Cookie logins (better-auth, Auth.js/NextAuth, Lucia, express-session) and localStorage tokens (Supabase) do. See `workspace-storage-state.ts`.
- **Clear browser data** (Headless (light) only) disposes the workspace's context without saving, deletes its storage file, and reopens its tabs in a new context at their URLs under the same ids. Other workspaces are untouched. The real-Chrome engines share one profile, so the menu hides it there (`status.engine.sharedStorage`).
- **Managed Chrome** is set up the way people run a Chrome for CDP by hand: real Chrome, a persistent profile with first run and metrics pre-answered, no automation switches. It has two modes, picked under Managed Chrome in Settings (`serverBrowser.chromeMode`).
- **Managed Chrome modes are separate Chromes with separate profiles**: `$PASEO_HOME/server-browser/chrome-profile-window` and `chrome-profile-headless`. Logins do not carry across, so you sign in to each; a session a site flagged as headless never reaches the windowed profile. Switching mode closes one Chrome and starts the other. The single `chrome-profile` of the first engines build becomes the Window profile on first start.
- **Window** (the default) runs headed on the first live X display (`DISPLAY`, then `/tmp/.X11-unix`), else on an Xvfb it starts and stops with Chrome, else `--headless=new`. The daemon launches that Xvfb through util-linux `setpriv --pdeathsig KILL`, so a killed daemon takes it down too; a host without `setpriv` stops it only on a graceful exit. On a host with a desktop (a VNC session, for example) its windows show on that desktop, where you can also use them; `PASEO_SERVER_BROWSER_DISPLAY=xvfb` keeps them on a private Xvfb, and `PASEO_SERVER_BROWSER_DISPLAY=:N` picks a display.
- **Headless** runs the same Chrome and flags with `--headless=new` and no display, and less memory (see Cost). New headless puts `HeadlessChrome` in its UA by design, so the daemon passes `--user-agent` with what this Chrome reports in a window: Chrome's reduced UA, built from the major version `--version` prints and the OS. That is the only thing it changes; `navigator.userAgentData` brands and the `Sec-CH-UA` header already match the windowed Chrome.
- **Both modes** skip Playwright's automation switches and add `--disable-blink-features=AutomationControlled`: on Chrome 153, `navigator.webdriver` is true for any CDP client, pipe or port, until that is off. Within a mode, one profile serves every workspace: a profile per workspace would mean a Chrome per workspace and a Google sign-in per workspace, and a context per workspace would lose IndexedDB and Google's own session state. Chrome keeps everything itself except session cookies (no expiry), which end with a browser session; the daemon carries those across its own restarts of Chrome, per mode (`$PASEO_HOME/server-browser/chrome-session`), saved every 30 s while tabs are open, before the last tab closes, and when Chrome closes.
- **Memory Saver is on, at Maximum, in both modes.** Each start writes it into the profile's `Local State` (`performance_tuning.high_efficiency_mode`, `state` 2 and `aggressiveness` 2, what the `MemorySaverModeSavings` policy's Maximum sets), which Chrome 153 honours; the policy itself would need a system-wide file, and an Existing browser's settings stay its owner's. It never unloads a Paseo tab, so a page an agent or viewer is using, or one with a dialog or upload pending, is never discarded: Chrome does not discard a tab that is active in its window or has a DevTools session attached, and every Paseo tab is the active tab of its own window with the daemon's session on it. Headless counts every window as visible, so the same holds there. Chrome's urgent discard under memory pressure keeps these protections too; only a discard a person asks for in `chrome://discards` unloads such a tab, and the daemon then drops it as a closed tab. The setting therefore saves no memory on Paseo's own tabs: in a 10-minute run with 5 idle tabs and 1 watched, Chrome used 397 MB with it and 395 MB without, with no discards either way. Suspending idle tabs (see What it does) is what frees a tab's memory.
- **Headed tabs each get a background window**, because Chrome stops painting a tab behind another in the same window, and the screencast would freeze. A headed Chrome keeps its startup window until the first tab exists: one with no window quits on the next profile write.
- **Existing browser** connects to `serverBrowser.cdpUrl` (`/json/version` gives the WebSocket). It opens Paseo's tabs in that browser's default context, so they share its logins, as background windows, so the owner's window keeps focus. The daemon acts only on targets it created, by id: it never closes, restarts or idle-exits that browser, never touches its other tabs, and on shutdown closes only its own tabs. It refuses downloads per page, because the browser-wide setting is the owner's. Other tools driving that browser (for example `agent-browser`, which acts on the active tab) can still reach Paseo's tabs.
- **Existing browser windows carry a title mark.** Paseo's windows sit beside the owner's, and CDP cannot name a window, so each Paseo tab's title reads `Paseo · <workspace> · <the page's title>` (`Paseo · <workspace>` for a page with none). The title observer (next bullet) puts the mark back each time the page sets its title, at most 10 times a second per document, and everything Paseo reports strips it again: the tab list, the viewer, the MCP tools' titles and the snapshot's document line. Past that rate the page keeps its own title unmarked until it loads a new document. A page whose own code puts its title back whenever it changes (an app's title observer that keeps `document.title` in sync) answers every mark with a write of its own; through v0.15.909 the two observers traded writes in a microtask loop that never yielded, so the page stopped answering, and each write sent Chrome's browser process a title update until it reached about 16 GiB and crashed (see Crashes, below). The owner's windows are never touched. Page scripts read the marked `document.title`; a page that builds a title from its own gets the mark once. A marker tab per window would also name it, but opening a tab activates its window and takes focus from the owner's on every new Paseo tab; no mark leaves the owner's windows indistinguishable from Paseo's. The name is read when the tab opens, so a renamed workspace shows its new name in tabs opened afterwards. Headless (light) and Managed Chrome have no owner's windows and no mark.
- **Titles are live.** Chromium sends no `Target.targetInfoChanged` for a title the page sets after it loads, so every tab runs a title observer (`window-title.ts`) in an isolated world that reports each change through a CDP binding (`Runtime.addBinding`, scoped to that world, so page scripts see neither). Tab lists, the viewer and the MCP tools show the page's current title.
- **CDP over a pipe** for the engines the daemon starts, not a TCP port: nothing else on the host can attach, and the browser exits when the daemon's end of the pipe closes, so a killed daemon leaves no orphan browser.
- **Sandbox.** Chromium starts sandboxed. If the kernel offers no usable sandbox (containers, this kind of Kubernetes pod), the daemon relaunches it with `--no-sandbox` and logs a warning once. Playwright does the same by default.
- **Two streams: video or JPEG.** A viewer that decodes video gets H.264 from Managed Chrome: the web app, Electron and phone browsers through WebCodecs (H.264 or VP8), and the iOS and Android apps through the `PaseoVideo` native view (H.264 only; see Native decoding). Every other viewer gets JPEG frames: any viewer of Headless (light) or an Existing browser, an app build without the native view, an app or daemon without video, and a viewer whose decoder failed three times in 10 s, which then asks for JPEG for that tab. Both arrive on the same stream id, and the viewer shows whichever painted last, so a capture that fails moves its viewers to JPEG without a new request. On the same pages, video holds 55–60 fps at 1.2–3.2 Mbit/s where JPEG needs 19–26 Mbit/s, and on a link of 200 ms and 20 Mbit/s JPEG falls to about 20 fps while video stays at 51–60 (see Cost).
- **Video.** An extension the daemon loads into Managed Chrome over CDP captures the tab (`chrome.tabCapture`) from its offscreen document and encodes it with WebCodecs; every chunk comes back through a CDP binding (`tab-video.ts`, `tab-video-extension/`). The capture and encoder code is adapted from [ace](https://github.com/arpan404/ace) (Apache-2.0; the notice is in each file). Branded Chrome ignores `--load-extension` since 137, so the daemon calls `Extensions.loadUnpacked`, which needs `--enable-unsafe-extension-debugging` over the CDP pipe; capturing without a user gesture needs `--allowlisted-extension-id`, pinned by the manifest's `key`. That is why only Managed Chrome gets video: chrome-headless-shell has no Extensions domain and no tab capture (`getDisplayMedia` throws `NotSupportedError`), and an Existing browser was started without the flags. Running Headless (light) on Playwright's full Chromium instead would give it video, at 306 MB instead of 160 MB for one tab; it stays the light engine. Capture survives navigations, and device sizes capture at the emulated pixels.
- **Encodes.** One capture per tab while someone watches, at the largest picture any viewer needs (capped at 1600 px). Each viewer sits on an encode: H.264 Constrained Baseline in Annex B (`avc1.42E028`), VP8 if the viewer cannot take H.264, hardware first with a watchdog: an encoder that takes frames and answers nothing for 1.5 s is replaced by the next configuration (software), and a stalled software encoder is restarted rather than failed, because a loaded host can stall it for seconds. A capture that restarts while Chrome still holds the tab's last one retries for up to 2 s. Viewers on the same load tier and about the same size share an encode; up to three per tab (`video-plan.ts`). The offscreen document closes 30 s after the last capture (it holds about 80 MB while capturing).
- **Video load tiers.** A viewer that starts dropping deltas twice within 2 s, for 0.5 s, moves from 60 fps to 30, for 3 s to 15, each tier its own encode at about 0.07–0.09 bit per pixel; 3 s without a backlog moves it back up one tier, and no tier changes for 2 s after the encodes change, because a change itself costs a keyframe. A slow phone never lowers a fast desktop's frame rate.
- **Native decoding.** React Native has no WebCodecs, so the apps decode in `packages/app/modules/paseo-video`: VideoToolbox into an `AVSampleBufferDisplayLayer` on iOS, `MediaCodec` onto a `TextureView` on Android. The native side only decodes and draws. TypeScript does the H.264 work (`h264-annexb.ts`): it splits the daemon's Annex B access units, hands each keyframe's SPS and PPS over apart, and sends the picture as AVCC to iOS and Annex B to Android. Acks, keyframe requests, recovery and the fall back to JPEG are one class for web and native (`video-session.ts`). A decoder that fails reports once, then drops deltas until a keyframe rebuilds it, so the frames queued behind a failure do not count as more failures. When the platform takes the decoder away (iOS invalidates a decompression session in the background, Android's `TextureView` gets a new surface) the native view reports it as interrupted: the viewer asks for a keyframe and starts over, and this never counts towards the three failures, so moving or backgrounding the panel cannot switch a tab to JPEG. A viewer releases its decoder as soon as video stops: the stream ends (hidden, resized, closed), the daemon moves it to JPEG (its first JPEG frame), or video is turned off. A chunk still in flight after that is acked and dropped, so it cannot start a decoder nothing would release. The app asks for video only when its build has the module (`requireOptionalNativeModule`), so an older build keeps JPEG.
- **JPEG.** One CDP `Page.startScreencast` per tab, running only while a JPEG viewer watches, at the largest size any viewer asked for (capped at 1600 px), quality 60. Chromium emits frames only when the page paints, so an idle page costs nearly nothing.
- **Flow control.** Each JPEG viewer has a window of unacked frames: 2 on a fast link, more on a long one, sized from its minimum ack round trip to allow about 15 fps (at most 8). A viewer out of window keeps only the newest frame; old frames are dropped, never queued. Chromium's own ack is released as soon as any viewer has room, so a slow phone never slows a fast desktop. See `screencast-hub.ts`. A video viewer's window is a round trip of its encode's frames plus three (6 to 90 chunks, at most 4 MiB), so a relayed viewer pipelines while a slow one never has more than a few frames queued: acks come after the viewer draws. A delta that does not fit is dropped, and that viewer skips deltas until a keyframe, which it asks for as soon as it has room; keyframes are never dropped. A viewer whose decoder fails asks for one too (`0x43`). The encoder spaces forced keyframes 500 ms apart, re-encodes the last frame when a still page owes one, and sends one every 6 s regardless (`video-hub.ts`, `tab-video-extension/pacing.js`).
- **Input.** Pointer coordinates travel as fractions of the frame, so clients never need the page's CSS size. Each input request takes one slot in the tab's CDP queue, so a release sent in its own request can never overtake the press before it. A move still waiting for its slot takes the newest position instead of queueing another, so a page slow to acknowledge input never builds a backlog in front of a click.
- **Hidden windows.** Chromium answers an input command only after the page handled the event, and the page of a minimized window, or of one on another desktop, is hidden and handles none. With the headed engines on a desktop that has a window manager, one such window used to hold its tab's queue for minutes, so Annotate's polls and click never ran. Before input from a viewer or an agent, and when a viewer starts watching, the tab now checks the page's visibility (a visible result is trusted for 500 ms). It restores a minimized window, which takes focus on that desktop as any restore does; a page that stays hidden fails the input with a message, and any input command unanswered after 5 s fails the same way.
- **Annotate.** `element-picker.ts` evaluates the browser preview's `selector-script.ts` unchanged (in a top-level tab its `window.parent` is the page, so its postMessage bridge talks to a small adapter the daemon injects) and polls the adapter every 80 ms. It reaches the page only through the tab's `TabContents` (`executeJavaScript`, `sendDebugCommand`), so it works on any engine that provides one, and polling keeps it to short calls in the tab's CDP queue instead of one long evaluate that would hold back input. Pointer moves and the click are ordinary input requests, so the hit test is the same as a click's. The crop is `Page.captureScreenshot` with the element's rect clipped to the layout viewport and moved into document coordinates (CDP's clip is document-relative), at the page's device scale factor. Chromium screencasts the clip-sized frame such a capture renders, so the tab drops any frame whose size is not its viewport's, and viewers keep the last page frame. Tab capture would show it too, so video pauses around any clipped or full-page `Page.captureScreenshot` (Annotate's crop, `browser_screenshot` of an element or a full page), and viewers resume at a keyframe. One pick per tab: a second start, from any client, cancels the first and waits for its teardown.
- **Loading pages.** Agent commands follow the desktop engine's loading semantics ([fork decision](fork-decisions.md#desktop-browser-loading-pages)): `new_tab`, `navigate` and `reload` settle at the new document's DOM-ready, not at a load event a hanging image delays forever, and a navigate past 10 s answers that the page is still loading and to call `browser_wait`. Navigation commands go outside the tab's command queue, because Chromium answers `Page.navigate` and `Page.reload` only once the server sends the document. While a navigation waits for its document, Chromium holds every command bound for the page (`Runtime`, `DOM`, `Input`; screenshots are not held) and runs it on the new document once that commits, whichever way the navigation started. The desktop runs scripts on the old document through Electron's frame IPC; the server has no such channel. So a script or snapshot then waits for the commit, at most 8 s and outside the queue, and past that fails telling the agent to call `browser_wait`. A script still awaiting when its document goes fails as "the page navigated". A woken tab still waits for its page's load event (at most 15 s) before it restores scroll and starts video.
- **Dialogs.** While a viewer watches the tab, `alert`, `confirm`, `prompt` and the leave-page (`beforeunload`) dialog wait for the user: the tab reports `dialog`, every viewer shows it over the page, and the first answer (`browser.server.tab.dialog.answer`) closes it for all. With nobody watching, or when the last viewer leaves, the dialog is accepted at once (prompt with its default) and recorded in the console, because a dialog holds the command that opened it and every later one. Input meanwhile fails at once with a message naming the dialog, instead of queueing behind it, and the answer goes outside the tab's command queue for the same reason. Through v0.15.909 every dialog was accepted automatically.

Protocol: gate on `server_info.features.serverBrowser`; video on `features.serverBrowserVideo` (the app then sends `video: { codecs }` on `browser.server.screencast.start.request`, and the response's `video: { codec }` says the stream sends `0x42` VideoChunk frames; without it the stream is JPEG), and the engine choice on `server_info.features.serverBrowserEngines` (older hosts get the on/off switch), Annotate element on `features.serverBrowserAnnotate`, the loopback ports a tab's page used (`browser.server.tab.loopback_ports`, for Open on this computer) on `features.serverBrowserLoopbackPorts`, the new-tab default on `features.serverBrowserTabTarget` (older hosts open every new tab in the server browser and hide the row), and suspended tabs on `features.serverBrowserSuspend` (the tab's optional `suspended`; an older app shows a suspended tab as a normal one, which reloads when viewed). An agent's tool answer carries the reload note in the response's optional `notice`. The app sends `serverBrowser.enabled` with every new-tab default change: the daemon parses a partial `serverBrowser` patch with `enabled` defaulting to false. The tab's `location` is an optional result field that only the daemon's router sets; `target` never reaches a browser host, so desktop apps of any version keep working. `browser.server.tab.annotate.start.request` stays pending until the user picks or cancels and answers with the selection and a base64 PNG; `browser.server.tab.annotate.cancel.request` ends it. RPCs and frames are in `packages/protocol/src/server-browser/rpc-schemas.ts` and `packages/protocol/src/binary-frames/server-browser.ts`. Every RPC needs `workspace.write` except the tab list (`workspace.read`): a frame shows the agent's signed-in pages, and input controls them.

## Crashes

An Existing Chrome that dies with `Trace/breakpoint trap` was stopped on purpose by Chrome itself: a failed `CHECK` or an out-of-memory crash, not a signal from outside. `--disable-breakpad` and `--disable-crash-reporter` do not stop crashpad from writing a minidump: they land in `~/.config/google-chrome/Crash Reports/completed/`, the default profile's folder, even for a Chrome on another `--user-data-dir`. A dump holds the browser's environment and URLs, so read it in place and quote none of it. Two facts tell the crashes apart without symbols (the binary is the installed `/opt/google/chrome/chrome`, so offsets match across dumps): the faulting offset into `chrome` from the exception stream, and, for an out-of-memory crash, the `alloc`, `commit` and `size` labels PartitionAlloc writes on the stack before it crashes. The 2026-11 crashes all faulted at one offset, with `commit` near 16 GiB and `size` 2 MiB: the browser process had filled its allocator pool. On a host with swap its RSS stays near 2 GB while that happens, so watch RssAnon plus VmSwap, not RSS.

## Known gaps

- Electron runs the same web viewer as the browser build (`surface.web.tsx`), and the browser build is what was verified. The desktop app itself has not been run against it.
- Video carries no audio: tab capture mutes the tab unless its audio is routed through an `AudioContext`, and the capture asks for none.
- A phone viewer has no pinch zoom. Use a phone size, or Responsive, for mobile layouts.
- New strings are English only.
- Same-site tabs of one workspace share a renderer process (`--process-per-site`), so a tab running a long script stalls its same-site siblings, and a renderer crash closes them together.
- With `--disable-gpu` the first screencast frame after a viewer attaches can be blank; the next paint replaces it.
- One browser serves every workspace, so a browser crash closes every workspace's tabs.
- In Managed Chrome and Existing browser, workspaces share one cookie jar: two dev servers on `localhost` with the same cookie name overwrite each other's sessions.
- Annotate cannot pick a button, link or form control itself: the selector script makes them click-through so pointing never presses them, and the pick lands on their parent. The web Browser behaves the same.
